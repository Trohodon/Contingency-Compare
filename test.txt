# Access Model Build Performance Improvements
## SCEG Model Ops

The purpose of these changes was to improve model build performance without
changing the intended model logic, output rules, or normal workflow.

---

# What was slowing the build down?

The main issue was not one single bad command.

The database was doing the same Access operations repeatedly inside large loops.

### Previous pattern

For each line or record:

1. Open or query a table
2. Look up one record
3. Run another query
4. Create or delete an Access query object
5. Repeat the same process for the next record

When this happens hundreds or thousands of times, the Access overhead adds up.

### Updated pattern

The new code tries to:

1. Filter records before they reach VBA
2. Open the needed recordsets once
3. Process those records directly
4. Reuse information already calculated
5. Close the recordsets and files cleanly

**The model is doing the same intended work with fewer database operations.**

# PowerWorld contingency writer

This was the largest performance improvement.

## Before

The contingency writer was doing several expensive operations repeatedly.

### 1. Broad Line scans

The code opened a broad set of Line records and then checked things such as:

- whether the line was a contingency
- whether it was active for the selected snapshot
- queue information

inside VBA.

That meant Access sent records to VBA that were later rejected.

## After

Those conditions are now pushed into the SQL query.

Example:

    SELECT *
    FROM Line
    WHERE InclAsCTG <> 0
      AND start_date <= snapshotDate
      AND end_date > snapshotDate

Only the records that actually need to be processed reach the VBA loop.

**Less data processed = less work.**

---

# PowerWorld contingency writer
## Removing repeated Access query creation

Another major issue was the Branch lookup.

### Before

For individual lines, the code repeatedly did the equivalent of:

    Delete saved query "filteredBranch"

    Create saved query "filteredBranch"

    Open "filteredBranch"

    Process records

Then it did it again for the next line.

That means Access was repeatedly creating and deleting database objects
during a single build.

### After

The SQL is opened directly as a read-only snapshot:

    Set filteredBranch = db.OpenRecordset(SQL, dbOpenSnapshot)

The query also filters the Branch records by:

- line ID
- start date
- end date

before VBA processes them.

### Why this is faster

We removed the repeated:

- QueryDef delete
- QueryDef creation
- saved-query opening
- unnecessary Branch records

from the inner loop.

---

# PowerWorld contingency writer
## Stop looking up information we already have

Queue logic was another area doing repeated work.

### Before

The current Line record already contained:

- Queue
- NotQueue

but the code would query the Line table again to retrieve that information.

Then it could query `QueuedProjects`.

If several lines referenced the same queue number, the same queue decision
could be calculated repeatedly.

### After

The current Line record supplies Queue and NotQueue directly.

The first time a queue project is checked, the result is calculated.

Later checks for the same queue information reuse that result during the build.

### In simple terms

**Before:**

    Ask Access the same question again.

**After:**

    We already know the answer — reuse it.

# The timing also shows where the improvement came from

The rest of the build did not suddenly become dramatically faster.

For example:

| Step | Before | After |
| --- | ---: | ---: |
| Load data | 44.1 sec | 45.9 sec |
| Branch data | 8.1 sec | 6.3 sec |
| Transformer data | 2.3 sec | 1.6 sec |
| UpdateDeviceData | 0.5 sec | 0.3 sec |
| **PowerWorld contingency** | **148.0 sec** | **5.0 sec** |

The load-data step actually stayed almost the same.

That is useful because it shows that the overall improvement was not
just normal timing variation.

The large improvement occurred in the area that was specifically changed.

# DeviceData cleanup

DeviceData was also doing unnecessary repeated Access work.

## Before

Similar DeviceData update logic existed in more than one writer.

The old process repeatedly used operations such as:

- opening destination tables
- DLookup
- action queries
- row-by-row database calls

## After

The DeviceData rebuild now uses one shared updater.

The updater:

- opens the source recordset once
- opens the destination recordset once
- works through the records directly
- keeps the existing duplicate-handling behavior

### Why this matters

Instead of repeatedly asking Access to perform individual operations,
the records are processed through an already-open recordset.

This reduces Access overhead and also removes duplicated code.

---

# Queued-project stability

The performance work also exposed some assumptions in the older code.

Queued projects can legitimately produce:

- empty recordsets
- missing optional DeviceData values
- Null fields

The older code sometimes assumed that a record would always exist.

That caused:

**Run-time error 3021 — No current record**

Checks were added before operations such as:

    MoveFirst
    MoveLast
    FindFirst

If a table is empty, the code now handles that condition instead of
trying to move to a record that does not exist.

---

# DeviceData Null handling

Queued-project testing also exposed:

**Run-time error 94 — Invalid use of Null**

Some DeviceData fields can legitimately be Null.

The old writer used those fields directly in:

- text operations
- numeric comparisons
- output strings

The updated writer checks or handles nullable values before using them.

Error cleanup was also added so an interrupted write does not leave
the DeviceData AUX file open and locked by Microsoft Access.

---

# What did NOT change?

The goal was to improve how the database performs the work,
not change what the model is supposed to produce.

The intended behavior remains the same for:

- model assumptions
- output file names
- PowerWorld AUX formatting
- contingency labels
- Branch outage formatting
- Queue / NotQueue rules
- regional bus-offset logic
- DeviceData rebuild behavior

The main changes are **how the data is retrieved and processed internally.**

---

# Bottom line

The speed improvement did not come from a new computer,
a different Access setting, or simply removing functionality.

It came from reducing repeated database work.

### Before

Open → Query → Lookup → Create/Delete → Repeat

### After

Filter → Open Once → Process → Reuse

## Proven result

**Total build**

3:32.6 → 1:11.4

**PowerWorld contingency file**

2:28.0 → 0:05.0

The database is doing substantially less Access work to produce
the same intended model output.
